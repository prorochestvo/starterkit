# Branches

- Commits on non-protected branches do not require separate approval.
- On `main`, `stage`, and `prod`, branch first. Direct commits or pushes require an explicit user request.
- Keep the history of `dev`, `main`, and the other integration branches linear: a work branch may hold any commits, including merges from its base, but it lands on the integration branch as one squash commit (`gh pr merge --squash`, or a branch-closing squash after rebasing the work branch onto the integration branch); never land a work branch as a merge commit or as its own commits.
- Promote `dev` into `main` as one squash commit every time unless the user asks otherwise; never fast-forward `main` to `dev` itself and never create a merge commit. Run `git commit-tree <dev-sha>^{tree} -p origin/main -F <message-file>` to build a commit whose tree is exactly the verified `dev` head and whose only parent is current `main`, so the pull request diff is exactly the new changes and never conflicts; check that `git diff <dev-sha> <new-sha>` prints nothing. Push that commit on a new short-lived branch, open a pull request into `main` so the required checks run on that very commit, and land it with `gh pr merge --squash` (one commit; message rules in `references/commits.md`). Pushing to and merging into `main` stays under `references/push.md` and the user's authorization; this rule grants no push or merge right. That short-lived branch is deleted under the deletion rule below like any other merged branch; the protection of a promotion pull request's head branch applies to `dev` and the other integration branches, not to it.
- Outside the GitHub issue delivery workflow, land several finished pieces of work on a protected branch together whenever they can land together, so its required checks run once instead of once per pull request: collect them on `dev` and promote it as above, or, in a repository without `dev`, on one short-lived branch cut from the protected branch and landed with `gh pr merge --squash`. Each work branch lands on that short-lived branch as one squash commit; the final squash into the protected branch may combine logical changes, overriding the atomic-commit rule in `references/commits.md`.
- After a squash lands on a branch, run `git fetch` and rebase onto `origin/<updated-branch>` each of your own open branches based on it, and `dev` after a promotion; leave another person's work branches to them. Use `git rebase origin/<updated-branch> <branch>` for a branch cut before the squash. For a branch that contains squashed commits, use `git rebase --onto origin/<updated-branch> <old-base> <branch>`, where `<old-base>` is the newest commit the squash already contains: the commit a stacked branch was cut from, or `<dev-sha>` for `dev` after a promotion. Before rebasing already-pushed commits, or pushing the rebased branch with `--force-with-lease=<branch>:<pushed-tip>`, obtain explicit approval under `references/push.md`, except for `dev` and your own work branch whose pull request targets `dev`, which need none.
- In the defined GitHub issue delivery workflow, branch from the repository default branch as `feat/<issue>-<slug>` or `fix/<issue>-<slug>`. Never commit directly to the default branch.
- Respect repository-specific branch policies and documented conventions.
- Do not leave a dump behind: once a branch's work has landed or been abandoned, delete the branch locally and on the remote, remove its worktree (`workflow/references/preflight.md`), and drop your own stashes, wip and backup branches. Before deleting, check yourself that the work is not lost; once the check below passes, delete without asking the user. Landed through a pull request: it reports `MERGED` (the rule below). Landed through a branch-closing squash: the branch was rebased onto the integration branch right before the squash, so `git diff <branch> <squash-commit>` prints nothing. Abandoned: the plan or backlog records it as dropped. Never delete the protected and integration branches, or a branch another person authored, that the rule below leaves in place.
- Delete a branch once its pull request is merged (`gh pr view <branch> --json state,headRefOid,author` reports `MERGED`): if `git ls-remote --heads origin refs/heads/<branch>` reports `headRefOid` as the branch's tip, run `git push origin --delete <branch>`; if the local tip equals `headRefOid`, run `git branch -D <branch>` (a squash-merged branch is not an ancestor of the base, so `git branch -d` refuses it). Leave `main`, `stage`, `prod`, `dev`, `alpha`, any branch the repository's working agreement names as its integration branch (a promotion pull request between them also reports `MERGED`), a branch with an open pull request, a branch checked out in a worktree, a local branch with commits beyond `headRefOid`, and a branch whose pull request another person authored; never delete the head branch of a merged promotion pull request (for example, `dev` into `main`).
