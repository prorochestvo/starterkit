## Overview

The owner's shared agent tooling (skills, helper scripts, hooks) lives only in the private
repository `ai-cli-config`, checked out as `~/.claude` on both of the owner's hosts. A new
machine or a new person cannot start from it, and the public `pipeline` plugin already
depends on it: `plugins/pipeline/agents/engineer.md`, `plugins/pipeline/skills/new-plan`,
`complete-plan` and `working-agreement` call `~/.claude/skills/task-management/...` and
`~/.claude/bin/{model-id,second-opinion.sh,codex-limits.py}`, which exist only on the owner's
hosts.

This plan publishes the shared part as a starterkit plugin, keeps the personal part in
`ai-cli-config` under the `.local` marker, and adds the controls that keep personal tokens
out of the public repository: a token gate that runs before every push, and an explicit
export manifest instead of "everything that is not `.local`".

Done means: a clean profile with no `ai-cli-config` installs the starterkit plugins and runs
a plan, a backlog capture, a second opinion and the commit-message hook end to end; both
owner hosts keep working throughout, with no window in which a live session loses a skill,
a script or a hook; and every push to starterkit made by this work passed the gate.

### Task 5: Export script from `ai-cli-config` to starterkit
- Description: `scripts/starterkit-export.sh` with an explicit manifest
  `scripts/starterkit-export.manifest` mapping source paths to starterkit paths
  (`skills/<name>` → `plugins/core/skills/<name>`, the shared `bin/` files →
  `plugins/core/bin/`, `agents/code-standards-auditor.md` → `plugins/core/agents/`, the two
  shared hooks → `plugins/core-hooks/hooks/`). It copies only `git ls-files` output (so `.env`,
  agent memory and caches never leave), skips every `*.local.*` file and `*.local` directory,
  drops `SKILL.md` table rows that reference a `.local.` path, and fails on any other `.local`
  mention. It works in a starterkit worktree on a new branch `export/<YYYYMMDD>`, bumps the
  `version` of each changed plugin, commits, then runs `public-gate.sh --tree` and `--range
  origin/main..HEAD` and `claude plugin validate` on each plugin. Drift guard: the script keeps
  `scripts/starterkit-export.state` (starterkit commit and per-file hash of the last export);
  a starterkit file whose hash on `main` differs from the recorded one stops the run with the
  diff, to be brought back into `ai-cli-config` by hand first. It never pushes.
- Acceptance Criteria:
  - `scripts/test-starterkit-export.sh` passes against a fixture repository: a `.local` file
    and a `.local` directory are skipped; a `.local` row is dropped and the rest of the table
    is byte-identical; a `.local` mention in prose fails the run; an untracked `.env` is not
    copied; a hand-edited starterkit file stops the run; a second run with no source change
    produces no commit;
  - a dry run against the real trees lists exactly the inventory's shared and split files;
  - the script refuses to run when the starterkit checkout is dirty or not on a fresh branch.
- Pitfalls & edge cases: starterkit-owned files (`plugin.json`, `hooks.json`, `README.md`,
  marketplace entry) are outside the manifest and never overwritten; a file removed from the
  manifest must be removed in starterkit by the export, not left orphaned; executable bits

## Risks

- A personal token reaches the public repository; pushed PR refs cannot be deleted. Controls:
  the explicit manifest (default deny), the gate in the export and in pre-push on both hosts,
  categories instead of values in this plan, and a hand check of the PR title and body before
  a squash merge.
- The two copies drift (D1 = mirror): an edit made in starterkit is lost on the next export.
  Control: the export's drift guard stops on any starterkit file that changed since the last
  export.
- The Linux host misses a step and its live sessions run a `pipeline` that calls names not on
  their `PATH`. Control: Task 7 lands before any merge; Task 8 merges only after both hosts
  pass the smoke checks.
- Licence: `pdf` cannot be published (D8); other vendor material must be checked the same way
  before it enters the manifest.
- Authority: Tasks 3–4 edit existing skills and scripts; instruction edits go through
  `skill-tuner`, script edits wait for the owner's approval, and `settings.json` is the
  owner's — the plan's pace depends on those approvals.

## Trade-offs

- Mirror over single copy (D1): two copies and an export script, in exchange for zero change
  to what the hosts load, unchanged `skill-tuner` routing, `.local` rows working as the owner
  defined them, and no public PR per remark. Reverse by enabling `core` on the hosts, deleting
  the bare skills and replacing the `settings.json` hook entries with `core-hooks` (the D1
  alternative).
- An explicit export manifest over "everything that is not `.local`": a new shared skill needs
  a manifest line, but a forgotten `.local` suffix cannot publish a personal file. Reverse by
  generating the manifest from `git ls-files` minus `.local`.
- Command names on `PATH` over absolute paths: depends on the plugin `bin/` and `env.PATH`, but
  the same text works for plugin users and on the owner's hosts. Reverse by restoring the
  absolute paths in the owner's copy only.
- A separate `core-hooks` plugin (D7): one more marketplace entry, in exchange for paid,
  data-sharing hooks being opt-in. Reverse by moving `hooks/` into `core`.
