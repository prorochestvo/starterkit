# Move the portable agent configuration into starterkit

- raised: 2026-10-15 — while auditing ai-cli-config before publishing it
- decision: open

The owner put the drafted plan on hold to think it over. The draft follows unchanged;
turning this entry into a plan starts from it.

## Owner direction (2026-10-21)

Where it conflicts with the draft below, this section wins.

- **Roles.** starterkit is what a new machine or a new person starts from: the shared skills,
  hooks, helper scripts and settings. `ai-cli-config` is the owner's personal backup: hosts,
  keys, backups and personal decisions. A shared file may exist in both; starterkit holds the
  source copy.
- **The glossary stays personal.** `GLOSSARY.md` is not moved and gets no generic template,
  which supersedes the draft's `templates/global/GLOSSARY.md`.
- **The `.local` marker.** These stay in `ai-cli-config` only, and the sync to starterkit skips
  them:
  - a file whose name carries `.local` before its extension (`actions-runner.local.md`,
    `ci-runner-setup.local.sh`);
  - a skill whose directory name ends in `.local` (`cli-my-skill.local`). Claude Code loads
    such a skill under that name (checked 2026-10-21); Codex is not checked yet.

  The sync also drops each `SKILL.md` reference-table row that points at a `.local.` file, so a
  skill keeps one `SKILL.md` for both repositories. First applied in `ai-cli-config` to the
  `cli-github` runner files (commit `41664c7`).
- **Classification** (to be confirmed per skill at migration time; personal facts inside a
  shared skill move to `.local` files first):

  | Shared, to starterkit | Personal, stays in `ai-cli-config` |
  |---|---|
  | `writing-instructions`, `cli-git`, `workflow`, `task-management` | `remote-access`, `cf-tunnel-registry` |
  | `common-contracts`, `skill-tuner`, `skill-incubator` | `cli-telegram`, `cli-jev`, `artifact-exchange` |
  | `ai-codex`, `ai-gemini`, `ai-claude`, `cli-openrouter`, `cli-cloudflare`, `pdf` (without `.env`) | the `cli-github` runner files (`.local`) |
  | `bin/model-id`, `bin/second-opinion.sh`, the commit-message and question-quorum hooks | `.env` files, keychain service names, `GLOSSARY.md`, `backup/` |

## Draft plan


### Overview

The reusable part of the owner's agent setup lives in the private `ai-cli-config`
repository (`~/.claude`) next to host-specific state: skills, hooks, helper scripts,
`AGENTS.md`, and `GLOSSARY.md` sit beside `backup/`, the host list, tunnel domains,
and personal preferences. That repository cannot be published, and the portable half
cannot be shared or installed on a new machine without the private half.

This plan moves everything portable into starterkit (public), in host-neutral form, and
leaves `ai-cli-config` holding only what is personal: identity, hosts, projects,
preferences, and backups. A new machine then needs the starterkit marketplace plus a
small private overlay; `ai-cli-config` stays private and needs no audit for publication.

### Assumptions

- starterkit stays public; nothing in it may name the owner's hosts, IPs, domains,
  accounts, organisations, or projects.
- Plugins cannot supply a user's global instructions: Claude Code reads `AGENTS.md` /
  `CLAUDE.md` from `~/.claude`, not from a plugin. The global files therefore ship as
  templates that a host's `~/.claude/CLAUDE.md` imports.
- `@path` imports work in `~/.claude/CLAUDE.md`, and the marketplace clone lives at
  `~/.claude/plugins/marketplaces/starterkit` on every host that registered it from
  GitHub (true on mac-m1 and hive-warden-01 since 2026-10-15).
- `${CLAUDE_PLUGIN_ROOT}` is expanded in plugin hook and MCP configuration, not inside
  skill Markdown; a loaded skill is told its base directory, so skills refer to their
  scripts relative to it.

### Decisions

| Decision | Choice | Rejected | Reverse by |
|---|---|---|---|
| Where the moved skills go | One new plugin, `core` | Into `pipeline`: mixes the plan-first pipeline with general tools; one plugin per skill: a dozen marketplace entries to keep in step | Move the skill directories; rename references |
| Skill names | `core:<name>` (`core:task-management`, `core:cli-git`, …) | Keeping bare names through a symlink farm in `~/.claude/skills`: two copies, drift | — |
| Global instructions | `templates/global/AGENTS.md` and `templates/global/GLOSSARY.md` in starterkit, generic; each host's `~/.claude/CLAUDE.md` imports them and adds `AGENTS.local.md` / `GLOSSARY.local.md` from `ai-cli-config` | Copying the templates into `~/.claude` (drifts from the source); keeping them private (nothing to share) | Replace the imports with the full text |
| Script paths in skills | Relative to the skill's base directory (`scripts/plan-name.sh`) | `~/.claude/skills/...` absolute paths: break for every other user | — |
| Hooks | `plugins/core/hooks/hooks.json` with `${CLAUDE_PLUGIN_ROOT}` | Per-host entries in `settings.json` | Re-add the entries to `settings.json` |
| Editing moved skills | `skill-tuner` commits on a branch in starterkit and opens a PR; the owner merges | Direct edits to the installed plugin cache: overwritten on update | Move the skill back to `~/.claude/skills` |

### Tasks

### Task 1: Personal-data sweep of the candidates
- Description: list every owner-specific token in the files that will move: account and
  organisation names, host names, IPs, ports, domains, emails, Telegram chat targets,
  project names, absolute home paths. Decide per hit: generalise, move into a
  `*.local.md` overlay, or keep the file private.
- Acceptance Criteria:
  - a checked list in this plan, one line per file;
  - `cli-github`'s runner reference (`ci-runner-01`, `prorochestvo-dev`) and
    `skill-tuner`'s Telegram step are split into a private overlay or made configurable.
- Pitfalls & edge cases: examples and test fixtures carry real names; `model-id` tables
  are fine (vendor ids, not personal).
- Complexity: Medium

### Task 2: Generic global templates
- Description: write `templates/global/AGENTS.md` and `templates/global/GLOSSARY.md`
  from the current files, keeping the rules and vocabulary that hold for any user and
  dropping the owner's register, hosts, projects, and paths. The personal remainder
  becomes `AGENTS.local.md` and `GLOSSARY.local.md` in `ai-cli-config`.
- Acceptance Criteria:
  - both templates contain no owner-specific token (Task 1 list applied);
  - `~/.claude/CLAUDE.md` = imports of the two templates plus the two local files, and a
    fresh session shows the same effective rules as before (diff of the rendered
    instruction text, ignoring order);
  - each template under 20 KiB.
- Pitfalls & edge cases: the template must not reference skills that stay private; the
  glossary's generic rows (`review`, `plan`, `backlog`, `owner feedback`, model aliases)
  go to the template, environment and project rows to the local file.
- Complexity: Medium

### Task 3: The `core` plugin
- Description: create `plugins/core` (manifest, marketplace entry), move the inventory's
  skills, helpers, and hooks, rewrite script references to skill-relative paths and hook
  commands to `${CLAUDE_PLUGIN_ROOT}`, and rename cross-references to `core:<name>`
  across starterkit (`pipeline` already points at `task-management` and its scripts).
- Acceptance Criteria:
  - `claude plugin validate` (or the marketplace load) passes;
  - no file under `plugins/core` contains `~/.claude/skills`, `~/.claude/bin`, or a
    `$HOME/.claude/hooks` path;
  - every script still runs from the installed plugin location (smoke: `plan-name.sh`,
    `backlog-triage.sh --list/--name/--gate`, `model-id sol`, `second-opinion.sh --help`,
    the commit-message hook on a sample message).
- Pitfalls & edge cases: `backlog-triage.sh` finds `model-id` through `$HOME/.claude/bin`
  today; scripts that call each other need a path relative to the plugin root.
- Complexity: Hard

### Task 4: Switch the hosts over
- Description: in `ai-cli-config`, delete the moved skills, helpers, and hooks, remove
  their `settings.json` hook entries, enable `core@starterkit` at user scope, and replace
  `AGENTS.md` / `GLOSSARY.md` with the import file and the local overlays. Update the
  `skill-tuner` route for plugin skills (branch and PR in starterkit). Roll out to
  mac-m1 and hive-warden-01.
- Acceptance Criteria:
  - on both hosts a new session lists `core:*` skills and no duplicate bare-named ones;
  - every hook fires once (no double registration from `settings.json` and the plugin);
  - `sync.sh` and `restore.sh` no longer reference the moved paths.
- Pitfalls & edge cases: the `settings.json` commit is owner-only; sessions must restart
  to load the plugin; references inside memory files and plans in other repositories
  still say `~/.claude/skills/...` and are history, not to be rewritten.
- Complexity: Medium

### Task 5: Verify on a clean profile
- Description: in a throwaway user (or `HOME`) with no `ai-cli-config`, register the
  marketplace, install `core` and `pipeline`, import the two templates, and run one plan
  and one backlog capture end to end.
- Acceptance Criteria:
  - skills load, scripts run, hooks fire, with no reference to a missing private path;
  - a final grep of starterkit for the Task 1 token list returns nothing.
- Complexity: Medium

### Risks

- A personal token slips into the public repository; once pushed it is public for
  good (pull-request refs are not deletable). Task 1 and the Task 5 grep gate this, and
  every push of this work runs the credential scanner.
- The import path into the marketplace clone is Claude Code internal layout; if it
  moves, global rules silently stop loading. Task 5 checks it; reversal is copying the
  templates into `~/.claude`.
- Skill names change from `task-management` to `core:task-management`: owner habits,
  memories, and other repositories' instructions that name the bare skill need the new
  name.

### Trade-offs

- Owner corrections to moved skills become pull requests to starterkit instead of
  direct commits in `~/.claude`: slower, but the public copy is the reviewed one.
- One plugin for all general tools is coarse; a user who wants only `cli-git` installs
  everything. Splitting later is a directory move.
