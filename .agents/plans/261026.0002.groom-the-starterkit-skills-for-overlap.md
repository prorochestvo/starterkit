# Task Breakdown

- status: draft (2026-10-26), to be reviewed and executed in the week of 2026-11-02.

## Overview

The starterkit plugins hold 35 skills (`core` 13, `pipeline` 5, `knowledge` 10, `stack-go` 5,
`stack-flutter` 1), and a host adds about a dozen private ones. Several of them describe the
same rule or the same moment from different angles, and several descriptions trigger on the
same request. The cost is concrete: an agent loads two skills for one task and follows the one
it read last; a rule changed in one place stays stale in the other; a description that claims
too much pulls a skill into tasks it does not own. The 2026-10-25 session showed both kinds:
the merge rule lived in `cli-github` while the merge handoff lived in `common-contracts`, and
the engineer's OpenRouter lane was described in `cli-openrouter`, `pipeline:engineer` and
`pipeline:working-agreement` at once.

Goal: every rule has one home, every other mention points there, and every description
triggers only on the tasks its skill owns. Grooming changes where text lives and how
descriptions read; it does not change what the rules say.

## Assumptions

- Skill instruction edits go through `skill-tuner`; this plan is the owner's order for a
  batch of them, applied as starterkit pull requests (one per cluster), each gated with
  `public-gate.sh` and stamped by the version workflow.
- Private skills (`~/.claude/skills`) are in scope only where they overlap a public one; their
  edits stay in the configuration repository.
- No skill is created, merged or removed without the owner's explicit approval
  (`skill-incubator`); a proposed merge is a finding for the owner, not a step of this plan.
- The 20 KiB per-file budget of `writing-instructions` holds after each change.

## Tasks

### Task 1: Map the overlaps
- Description: for each cluster, read the skills in full (with their references) and record
  every rule stated in more than one place, every description phrase that triggers more than
  one skill, and every cross-reference that points to a moved or renamed rule. One table per
  cluster: rule or trigger, where it appears, proposed home, proposed change.
- Acceptance Criteria:
  - Every cluster has a table, or a line saying it has no overlap.
  - Each row cites file and line.
  - The map is reviewed (`workflow` review cycle for plans) before any edit.
- Pitfalls & edge cases: a deliberate summary that points to its home is not a duplicate;
  two skills may state the same fact for different audiences (agent versus human README).
- Complexity: Medium

### Task 2: Descriptions
- Description: rewrite the `description` of each skill whose trigger overlaps another, so
  each names only the tasks it owns and, where useful, the skill that owns the neighbouring
  task. Test each description set by asking a fresh `claude -p` session which skill it would
  load for 20 sample requests drawn from real prompts.
- Acceptance Criteria:
  - For the sample requests, exactly one skill (or the intended pair) is chosen.
  - No description exceeds the platform limit.
- Pitfalls & edge cases: a narrower description can stop a skill from loading where it is
  needed; keep the Russian trigger phrases the owner uses.
- Complexity: Medium

### Task 3: One home per rule
- Description: per cluster, move each duplicated rule to its home and replace the other
  copies with a one-line pointer, one pull request per cluster, through `skill-tuner`.
- Acceptance Criteria:
  - The map's rows for that cluster are closed.
  - `claude plugin validate --strict` and the public gate pass.
  - No rule's meaning changes (the diff of each rule's home reads as a move, not an edit).
- Pitfalls & edge cases: `pipeline` and `core` version separately; a pointer from
  `pipeline` to `core` assumes `core` is installed (it is a declared dependency since #36).
- Complexity: Hard

### Task 4: Findings for the owner
- Description: list the cases where the map suggests merging, splitting or removing a
  skill, with the reason, for the owner's decision.
- Acceptance Criteria: the list is in the plan; nothing in it is applied without approval.
- Complexity: Easy

## Execution Order

1. Task 1 (review of the map)
2. Task 2 and Task 3, cluster by cluster
3. Task 4

## Risks

- A moved rule loses context its old home gave it; mitigated by keeping the pointer and
  reviewing each cluster's diff as a move.
- Hosts load the change only after a marketplace update; until then sessions run the old
  text (hosts are updated by hand).

## Trade-offs

- One pull request per cluster instead of one for all: more merges, but each can be
  reverted on its own.
- Pointers instead of copies: an agent may need to load one more file, in exchange for a
  rule that cannot drift.
